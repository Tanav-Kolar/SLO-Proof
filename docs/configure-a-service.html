SLOProof · operator reference · forge-tyr

Configure a service

SLOProof puts a service under evidence-gated recovery: an agent proposes a route change, and a deterministic verifier reading Elasticsearch decides whether the measurements allow it to expand. Everything below is what a service has to supply before a run can produce a verdict — identity, two versions, one weighted route, an evidence path, and a frozen contract. checkout is the reference implementation; the defaults in every field are its real values.

§

What you supply, what you reuse

The reusability claim, stated as two lists

Reuse is the point: a second service should be configuration, not a second orchestrator. The spine below is service-agnostic today. The right-hand column is the work, and the last two rows of it are the ones that cannot be filled in by copying checkout.

Shared spine — reuse unchanged

One controller, one verifier, one ledger

  • Indices sloproof-requests, -contracts, -ledger with strict mappings
  • Three scoped keys ingest writes, verifier only reads, controller writes contracts and ledger
  • Load generator constant arrival rate, bulk shipper, -service flag
  • Guard scripts/_guard.sh pins the kubeconfig and asserts the context
  • Weight executor set-weights.sh rewrites weights on backends the route already names
  • ES|QL queries parameterized by run and window

Per service — you supply

Identity, workloads, route, contract

  • Identity service name, namespace, app label, route name
  • Two versions a known-good and an incident configuration of one image
  • One HTTPRoute with exactly one header-free rule and exactly two backends
  • A contract naming the service it governs, with its own thresholds
  • A correctness check beyond HTTP 200 — search needs a result fixture, auth needs invalid credentials still rejected
  • An SLO-bearing endpoint that echoes correlation headers and its config hash
The honest version

Checkout proves the routing and the evidence path, not the reuse. The verifier that turns measurements into PROVED does not exist yet (src/control/), and three scripts still carry the name checkout in code rather than in configuration. Both are listed under known gaps.

05

Freeze the acceptance contract

Criteria are evidence, not knobs to turn after seeing the trial

Freeze one contract document before the first recovery weight change. Store the exact body, its SHA-256 hash, the service and run identities, who froze it, and the freeze time in sloproof-contracts. Every later receipt and verdict must carry that same hash. If the service identity, route, criteria, or behavior fingerprint changes, expire the trial and begin a new run; never edit a contract in place.

shell · produce stable bytes and record the freeze 
CONTRACT=contracts/checkout-slo.json
CANONICAL=$(jq -cS . "$CONTRACT")
CONTRACT_HASH=$(printf %s "$CANONICAL" | shasum -a 256 | awk '{print $1}')
FROZEN_AT=$(date -u +%Y-%m-%dT%H:%M:%SZ)

# Store CANONICAL unchanged in sloproof-contracts with:
# run_id=demo-1, service=checkout, contract_hash,
# frozen_at, frozen_by, and the /version snapshots for both versions.
printf 'contract %s frozen at %s\n' "$CONTRACT_HASH" "$FROZEN_AT"
A hash proves identity, not immutability

Elasticsearch privileges do not make an indexed contract append-only. The hash lets every consumer prove it evaluated the same bytes; organizational controls and scoped credentials prevent replacement. If a stored body and its hash disagree, the only safe result is INCONCLUSIVE.

06

Collect the verdict inputs

Completeness first, metrics second, promotion last

Wait for 30 seconds of ingestion allowance after each window closes, then run the saved queries with the read-only verifier key. The verifier must evaluate 3 closed, non-overlapping windows anchored to the observed route_effective_at. Planner prose, agent output, a successful route patch, and a requested 10/90 split are not verdict inputs.

OrderSaved query / evidenceGateFailure result
1evidence-completenesseach version has ≥ 400 samples, one config hash, and a closed time rangeINCONCLUSIVE

3traffic-splitserved counts demonstrate the bounded trial actually occurredINCONCLUSIVE
4window-metricssuccess ≥ 0.99 and p95 < 300 ms for every required windowFAILED on a measured breach
5provenance snapshotsroute UID, contract hash, image digest and both config hashes still match the freezeINCONCLUSIVE
shell · one closed window, inclusive start and exclusive end 
export WINDOW_START='<route_effective_at + convergence allowance>'
export WINDOW_END='<WINDOW_START + 60s>'

elastic/query.sh evidence-completeness \
  run_id=demo-1 window_start="$WINDOW_START" window_end="$WINDOW_END"
elastic/query.sh traffic-split \
  run_id=demo-1 window_start="$WINDOW_START" window_end="$WINDOW_END"
elastic/query.sh window-metrics \
  run_id=demo-1 window_start="$WINDOW_START" window_end="$WINDOW_END"

Verdict semantics

Decisive results

Measured pass or measured breach

  • PROVED every required window is complete and every criterion passes.
  • FAILED evidence is complete and at least one measured criterion breaches.

No decision

Missing evidence is never success

  • INCONCLUSIVE for empty, stale, underpowered, inconsistent, or unreconciled evidence.
  • Promotion is forbidden for both FAILED and INCONCLUSIVE.

Agents remain outside the decision path

shell · advisory, explanation, and judge questions 
scripts/agent.sh preflight --run-id demo-1
scripts/agent.sh investigate --run-id demo-1 \
  --window-start "$WINDOW_START" --window-end "$WINDOW_END"

# Only after the deterministic verifier has written a verdict:
scripts/agent.sh narrate --run-id demo-1
scripts/agent.sh ask --run-id demo-1 \
  "what share of traffic did v1 serve during the trial?"

The investigator can recommend, the narrator can explain an existing verdict, and the briefer can answer questions with cited query IDs. None may write a verdict or patch the route. Promotion is a separate executor action and is permitted only when a valid PROVED record names the expected contract hash, route UID, and current weights.

Stop conditions

Stop without promotion if any window is still open, the route effective time is unknown, the load generator cannot reconcile counts, either version is underpowered, more than one config hash appears, the contract or route identity changed, or the verifier is unavailable. Waiting or escalating is safer than turning absence into a pass.

!!

Known gaps before this is reusable

What the repository does not yet justify claiming

  1. The deterministic control plane is not implemented

    src/control/ is absent. The repository has measurements, saved ES|QL queries, routing scripts, and agent advisories, but no program that freezes a contract, evaluates all windows, writes a verdict, or conditionally promotes.

    Close it: implement the verifier and ledger writer first; add the state machine and expiry watchdog after the two verdict scenarios are reproducible.

  2. The load generator is not packaged for in-cluster execution

    The first real run measured from the operator laptop and added enough network latency to fail healthy v1. There is no load-generator image or Kubernetes workload in this repository yet.

    Close it: build and deploy loadgen beside the gateway, then measure index-visibility lag and replace the provisional 30-second allowance.

  3. Service reuse is documented, not automated

    The scripts and manifests still contain checkout-specific filenames, resource names, placeholders, and CHECKOUT_IMAGE. This browser configurator updates examples only; it does not write repository files.

    Close it: introduce one validated service descriptor and render manifests, contracts, and commands from it in CI.

  4. Route effectiveness is not observed automatically

    Weight receipts correctly leave route_effective_at null, but no controller fills it from served-traffic evidence. A patched HTTPRoute therefore cannot start a verification window by itself.

    Close it: require a stable observed split before stamping the effective time, and bind that observation to the receipt's route UID and resourceVersion.

  5. The local smoke script can report a false green

    It uses fixed ports, does not prove the process it started owns them, prints metrics without asserting the contract, and can exit zero when another service answers. Treat its current output as diagnostic, not a test result.

    Close it: allocate free ports, fail on bind errors, verify /version identity, and assert the expected success and latency ranges.

  6. Correctness remains service-specific

    HTTP status and latency are enough for the simulated checkout, not for an arbitrary production API. A fast 200 with the wrong body can still be a failed recovery.

    Close it: attach an operator-owned correctness probe or fixture to each service contract and ingest its result as explicit evidence.

02

Two versions of one image

The regression must be a configuration difference, not a second build

checkout-v1 and checkout-v2 run the same binary and differ only by ConfigMap. Say that out loud in the demo: the recovery is a configuration rollback, not a code revert. The routing proof is unaffected — traffic really does move between two independently addressable versions.

Faults are read from the environment at process start. There is deliberately no fault-toggle endpoint: the recovery executor must not be able to cause the incident it is trusted to repair. Profiles are changed by the operator, under the operator's identity, with a rollout.

Fault profiles

Presets live in src/checkout/profiles.json and are selected with FAULT_PROFILE; explicit env beats the preset, so a one-off experiment never requires editing the file. Measured locally over 300 requests at 40 concurrent:

ProfileInjectedSuccessp95Role in the run
healthynone 100%82 ms baseline and recovery candidate — passes the contract with room
checkout-regression+800 ms, 500 every 5th request 80%878 ms the incident
bad-recovery+450 ms 100%541 ms successes alone are not a recovery — latency breach, FAILED
Two properties are load-bearing

Deterministic. Errors come from an atomic request counter and jitter from the request sequence via splitmix64, so a rerun reproduces the distribution. Counters are per-pod and reset on restart — note that when reconciling a window that spans a rollout.

Scoped to the SLO path. Health probes are never faulted. If liveness tracked injected errors, Kubernetes would restart the faulty version and delete the incident before it could be measured.

What a new service has to expose

Four endpoints and three headers. Without them the evidence cannot be attributed and the verifier cannot exclude what the contract excludes.

03

One weighted route

Rule order is load-bearing; only one rule is executor-writable

The route carries three rules. Two are operator-owned pins selected by x-sloproof-target, so synthetic journeys and preflight checks can address one version directly; that traffic is labelled synthetic and excluded from the counts the verifier reads. The third is ordinary traffic and is the only rule the recovery executor may modify — and only its backendRefs weights.

set-weights.sh finds that rule by shape — the single header-free rule — rather than by a fixed index, and refuses if that is ambiguous. It then rewrites the weights on whatever backends the route already names. Hardcoding backend names would both break reuse and silently clobber a backend somebody else had edited.

k8s · the ordinary-traffic rule 
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: checkout-route
  namespace: checkout
spec:
  parentRefs:
    - { name: checkout-gateway }
  rules:
    # 0,1 — operator pins. Omitted here; matched on x-sloproof-target: v1|v2.
    # 2  — ordinary traffic: exactly one header-free rule, exactly two backends.
    - matches:
        - path: { type: PathPrefix, value: /checkout }
      backendRefs:
        - { name: checkout-v1, port: 80, weight: 100 }
        - { name: checkout-v2, port: 80, weight: 0 }

The four phases

PhaseCommandSplitWho runs it
Healthy baselineset-weights.sh 100 0100 / 0operator
Incidentset-weights.sh 0 1000 / 100operator — label it manual unless detection is automated
Recovery trialset-weights.sh 10 9010 / 90executor, on an allowed action
Promotionset-weights.sh 100 0100 / 0executor, only on PROVED
Receipts record two times, and one of them starts null

Every weight change writes a receipt to evidence/ with the route UID, resourceVersion before and after, and both weight sets. route_effective_at is left null on purpose: an accepted API patch is not evidence that traffic moved, so it must be filled from observed served traffic. Observation windows anchor to that second timestamp — never to API acceptance, and never to planner text.

04

The evidence path

Client-observed outcomes, three scoped keys, one stable document id

The verifier's source of truth is what the client observed, not what the service logged: only the client sees timeouts and gateway failures that never reached a pod. Records ship by _bulk off the timing path, with request_id as the document _id so a retried bulk item overwrites instead of double-counting. These are regular indices, not data streams — data streams force generated ids.

shell · once per cluster, then once per service 
# Index templates + concrete indices. Reads .env, never prints it.
elastic/setup.sh

# Three scoped keys. Needs ELASTIC_USERNAME/PASSWORD: an API key cannot mint
# a scoped child key, only a derived one that inherits everything.
elastic/create-api-keys.sh

# Load generator — run it INSIDE the cluster (see the warning below).
src/loadgen/loadgen \

  -service checkout \
  -run-id demo-1 \
  -rps 100 -duration 0 -warmup 10s \
  -traffic-class ordinary \
  -index sloproof-requests -batch-size 500 -flush-interval 2s
D9 — the finding that invalidated the first real run

Healthy v1 measured a p95 of 339 ms against a 300 ms threshold, which would have returned FAILED for a service that was working correctly. The service was not the cause: the same request from inside the cluster completes in about 50 ms, while from the operator's laptop the TCP connect alone cost 245 ms. The generator was running trans-Pacific.

Put the vantage point next to the service, or the contract measures the demo operator's geography. Until the generator runs in-cluster, no run can produce PROVED.

Three keys, because the decider must not be able to write the evidence

The unrestricted key in .env is for setup only and must not be used by any runtime component. State the limit honestly in the presentation: RBAC restricts resources and verbs, not individual fields — weight-only mutation is enforced by executor validation, and a contract hash is traceability, not privilege-enforced immutability.
